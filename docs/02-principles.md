# Software Engineering Principles in Wahala Sorter

*Every principle used in this codebase, explained in plain words with exact lines.*

---

## 1. Separation of Concerns

**Plain words**: Each file minds its own business. Type definitions don't mix with UI code. Styles don't mix with logic. The entry point doesn't build the app.

| File | Job | Lines |
|---|---|---|
| `types.ts` | Defines shapes of data (Task, Column, ColumnId) | 1–14 |
| `App.tsx` | App logic + UI rendering | 1–148 |
| `index.css` | Global/base styles (reset, colours, body) | 1–37 |
| `App.css` | Component-specific styles (board, columns, tasks) | 1–220 |
| `main.tsx` | Entry point — mounts React into the DOM | 1–10 |
| `index.html` | HTML shell — loads fonts, shows the door | 1–15 |

If you want to change the timestamp format, you go to `App.tsx`. If you want to change the page background colour, you go to `index.css`. If you want to change how many columns there are, you go to `types.ts` and `App.tsx`. Every concern has a home.

## 2. Single Responsibility Principle

**Plain words**: Every function does exactly one thing. If you can't describe it in one short sentence, it's doing too much.

| Function | One Job | Lines |
|---|---|---|
| `formatTime(ts)` | Convert a timestamp into a human "how long ago" string | `App.tsx:11–20` |
| `addTask(e)` | Take typed input, create a new task, clear the box | `App.tsx:36–42` |
| `deleteTask(id)` | Remove one task by its ID | `App.tsx:44–46` |
| `moveTask(id, to)` | Change which column a task lives in | `App.tsx:48–51` |
| `handleDragStart(e, id)` | Put the task's ID on the clipboard for dragging | `App.tsx:53–56` |
| `handleDragOver(e, col)` | Allow dropping and mark which column is targeted | `App.tsx:58–62` |
| `handleDragLeave()` | Clear the drag-over highlight | `App.tsx:64–66` |
| `handleDrop(e, col)` | Read the dragged task's ID and move it to the target column | `App.tsx:68–72` |

Each CSS class also has one job:
- `.title` (`App.css:11`) — styles only the title
- `.task-delete` (`App.css:182`) — styles only the delete button
- `.empty-state` (`App.css:134`) — styles only the empty column message

Each class describes what it does, and it only knows about itself.

## 3. Immutability

**Plain words**: Never change the original data. Always make a copy with your changes, then replace the whole thing. Like editing a photocopy instead of the original document, then throwing the old original away.

```tsx
// App.tsx:40 — Make a new array with the old tasks PLUS one new task at the end
setTasks(prev => [...prev, {
  id: String(nextId++),
  title,
  column: 'now',
  createdAt: Date.now()
}]);

// App.tsx:45 — Make a new array WITHOUT the deleted task (filter returns a new array)
setTasks(prev => prev.filter(t => t.id !== id));

// App.tsx:49 — Make a new array where the moved task gets a COPY with column changed
setTasks(prev => prev.map(t => t.id === id ? { ...t, column: to } : t));
                                                  // ^^^ spread operator = copy
```

Three patterns used:
- **Spread syntax** (`...prev`, `...t`) — copies old data into a new container
- **`filter()`** — returns a brand new array, doesn't touch the old one
- **`map()`** — returns a brand new array, each element is either the original or a copy

Why this matters: if you mutate the old array directly, React doesn't know the data changed. The screen stays frozen. Immutability guarantees React can detect changes by simple reference comparison (`oldTasks !== newTasks`).

## 4. Composition

**Plain words**: Build big things by nesting small things. Like Lego — a column is a box, a task card is a smaller box inside it, a timestamp is a tiny piece inside the card.

```
<App>                          ← App.tsx:74–145
  <header>                     ← :76  (title + subtitle)
  <form>                       ← :83  (input + add button)
  <div class="board">          ← :96  (the three-column grid)
    <div class="column">       ← :100 (Now column)
      <div class="column-header">   ← :107
      <div class="column-body">     ← :115
        <div class="task">     ← :120 (each card)
          <div class="task-content">  ← :126
          <button>             ← :130 (delete)
  <div class="column">...      ← (Soon)
  <div class="column">...      ← (Later)
```

The columns are generated by mapping over the `COLUMNS` array (`App.tsx:97`), so adding a fourth column means adding one entry to the array — the composition takes care of the rest. The whole structure emerges from small, predictable pieces.

## 5. Type Safety / Static Typing

**Plain words**: You tell the computer the shape of your data ahead of time. If you try to put a square peg in a round hole, TypeScript yells at you before the app even runs.

```tsx
// types.ts:1
export type ColumnId = 'now' | 'soon' | 'later';
// A column ID can ONLY be one of these three strings. Not "maybe", not "urgent".

// types.ts:3-8
export interface Task {
  id: string;        // must be a string, not a number
  title: string;     // must be a string
  column: ColumnId;  // must be 'now', 'soon', or 'later'
  createdAt: number; // must be a number (milliseconds)
}

// App.tsx:32 — useState is told "this holds an array of Task objects"
const [tasks, setTasks] = useState<Task[]>(INITIAL_TASKS);

// App.tsx:36 — FormEvent tells TypeScript "this handler receives a form submit event"
const addTask = useCallback((e: FormEvent) => { ... }, [input]);
```

If someone tries to do `task.column = 'urgent'`, TypeScript refuses to compile. The error catches it before the code ever reaches a browser.

## 6. Declarative Programming

**Plain words**: You describe WHAT you want to see, not HOW to build it step by step. Instead of "create a div, then loop, then append children", you say "this div contains a list of these items."

```tsx
// App.tsx:97 — "For each column, render a column div"
{COLUMNS.map(col => ( ... ))}

// App.tsx:119 — "For each task in this column, render a task div"
{colTasks.map(task => ( ... ))}

// App.tsx:116 — "If there are zero tasks, show this empty message"
{colTasks.length === 0 && (
  <p className="empty-state">Empty. For now.</p>
)}
```

No `for` loops, no `createElement()`, no `appendChild()`. Just "here's what the screen should look like given this data." The framework figures out the HOW.

## 7. DRY (Don't Repeat Yourself)

**Plain words**: If you write the same thing twice, you're doing it wrong. Put it in one place and reference it.

```tsx
// App.tsx:5-9 — Column definitions live ONCE in an array
const COLUMNS = [
  { id: 'now', label: 'Now', description: 'Right now, no delay' },
  { id: 'soon', label: 'Soon', description: 'Today or tomorrow' },
  { id: 'later', label: 'Later', description: 'This week, insha Allah' },
];

// Then used once with .map() at line 97 — no copy-pasting three column divs
```

```css
/* index.css:7-19 — Colours defined ONCE as CSS variables */
:root {
  --now: #C75B3A;
  --soon: #3F7D6A;
  --later: #8A7B70;
}

/* Reused everywhere by name instead of repeating hex codes:
   App.css:52  → border-color: var(--now);
   App.css:57  → background: var(--now);
   App.css:143 → color: var(--now);  (for the column title)
   App.css:204 → color: var(--now);  (delete button hover)
*/
```

Without DRY, changing a column description means editing three separate places. Without CSS variables, changing a colour means searching and replacing across the entire stylesheet. With DRY, you change one value and everything updates.

## 8. Pure Functions

**Plain words**: Give a function the same input, you always get the same output. It doesn't look at or change anything outside itself. Like a vending machine — press B3, always get Fanta.

```tsx
// App.tsx:11-20 — formatTime is a function that reads a timestamp
function formatTime(ts: number): string {
  const diff = Date.now() - ts;
  ...
}
```

**Caveat**: This one is technically *impure* because `Date.now()` changes every millisecond. However, the function has no *side effects* — it doesn't change any files, write to the screen, or modify any variables outside itself. It only reads the clock and returns a string. In practice, this is the right trade-off for a "time ago" display, but a truly pure version would accept `now` as a parameter too.

A pure function is easy to test, easy to reason about, and easy to move around. An impure function carries hidden dependencies that can break in unexpected ways.

## 9. Encapsulation / Data Hiding

**Plain words**: Data and the code that changes it live close together. Nothing outside can reach in and mess with the state directly.

```tsx
// App.tsx:32 — tasks lives inside the App function. No other file can touch it.
const [tasks, setTasks] = useState<Task[]>(INITIAL_TASKS);
// You can ONLY change tasks through setTasks. No direct mutation.

// App.tsx:44-46 — The only way to delete is through this handler
const deleteTask = useCallback((id: string) => {
  setTasks(prev => prev.filter(t => t.id !== id));
}, []);
```

The `input` state (`App.tsx:33`) and `dragOver` state (`App.tsx:34`) are also encapsulated inside `App`. Nothing outside can reach in and set them. All changes go through the exposed handlers. This means you can trust your data — you know exactly where and how it changes.

## 10. Unidirectional Data Flow

**Plain words**: Data flows DOWN from parent to child. Events flow UP from child to parent. No spaghetti.

```
State (tasks) lives in App ↓
  → Board reads tasks ↓
    → Column filters its own tasks ↓
      → Task card displays data

Events flow UP:
  User types in input → onChange → setInput (state goes up to App)
  User clicks × → onClick → deleteTask(id)
  User drops task → onDrop → handleDrop → moveTask(id, col)
  User submits form → onSubmit → addTask
```

No child component modifies state directly. They call functions passed down to them (or in this case, imported from the same file since everything is in `App.tsx`). You can trace every state change to a single user action.

## 11. Memoization / Performance Optimization

**Plain words**: Don't do work you already did. If nothing changed, use the old result. Like remembering where you put your keys instead of searching the house every time.

```tsx
// App.tsx:36 — Only recreate addTask when 'input' changes
const addTask = useCallback((e: FormEvent) => { ... }, [input]);

// App.tsx:44 — Never recreate deleteTask (its logic doesn't depend on changing values)
const deleteTask = useCallback((id: string) => { ... }, []);

// App.tsx:48 — Never recreate moveTask
const moveTask = useCallback((id: string, to: ColumnId) => { ... }, []);

// Same for handleDragStart, handleDragOver, handleDragLeave
// App.tsx:68 — handleDrop DOES depend on moveTask
const handleDrop = useCallback((e: React.DragEvent, col: ColumnId) => {
  ...
}, [moveTask]);
```

The dependency array `[input]` or `[]` or `[moveTask]` tells React: "Only give me a new function if these things changed." Empty array = "this function never changes, keep the same one forever."

Without `useCallback`, every render creates new function objects. React sees "the onClick prop changed" and has to re-render child components. With `useCallback`, the function reference stays the same, and React can skip unnecessary re-renders.

## 12. Progressive Disclosure

**Plain words**: Show the basics first. Reveal advanced features only when the user needs them. Don't overwhelm.

```tsx
// App.tsx:130-136 — Delete button is HIDDEN until you hover over the task
<button className="task-delete" ...>&times;</button>

// App.css:199-201
.task:hover .task-delete {
  opacity: 1;  /* Appears only on hover */
}
```

The × button is invisible by default (`opacity: 0` at line 194). It only appears when you hover over a task (`opacity: 1` at line 200). The interface stays clean until you need the power.

This principle is everywhere in good UI: advanced settings are behind a cog icon, full error details are behind "Show more", the delete action is hidden until you're interacting with the specific item. The interface reveals complexity gradually, reducing cognitive load for new or casual users.

## 13. Defensive Programming / Guard Clauses

**Plain words**: Check for problems at the door. If input is bad, leave immediately instead of crashing later.

```tsx
// App.tsx:38-39
const title = input.trim();  // Remove leading/trailing spaces
if (!title) return;          // If empty after trim, do NOTHING
// Only reached if there's real text

// App.tsx:70-71
const id = e.dataTransfer.getData('text/plain');
if (id) moveTask(id, col);   // Only move if we actually have an ID
// Prevents crashing if drag data is missing
```

Guard clauses are the "if it fits, it sits" of programming. You check the condition early. If it's bad, you bail out immediately. The alternative is nested `if` statements or trying to operate on invalid data and crashing. A guard clause at the door keeps the rest of the function clean and safe.

## 14. Responsive Design / Adaptive Layout

**Plain words**: The same app looks good on a phone, tablet, or big monitor. Not by shrinking, but by rearranging.

```css
/* App.css:207-220 */
@media (max-width: 700px) {
  .board {
    grid-template-columns: 1fr;  /* Three columns STACK into one */
  }
  .add-form {
    flex-direction: column;     /* Input on top, button below */
  }
}

/* App.css:13 — Title grows/shrinks with screen */
font-size: clamp(2rem, 5vw, 3rem);
/* On a 400px phone: 5vw = 20px, so clamp gives 2rem (32px)
   On a 1200px desktop: 5vw = 60px, so clamp gives 3rem (48px)
   Between: fluid scaling */
```

Three different tricks at play:
- `clamp()` — fluid typography that scales smoothly between min and max
- `@media` — breakpoints where the layout fundamentally changes (columns → single column)
- `fr` units — equal fractions of available space, no pixel math needed

The result: the app works on a 6-inch phone and a 27-inch monitor without looking broken on either.

## 15. Accessibility (a11y)

**Plain words**: Make sure everyone can use the app, including people who can't see the screen and use a screen reader.

```tsx
// App.tsx:133
aria-label="Delete task"
```

This single attribute tells a screen reader "this button deletes the task" instead of just reading "times" (the × symbol). A sighted person sees the ×, a blind person hears "Delete task."

`aria-label` is one of the smallest changes you can make with one of the biggest impacts. It costs nothing — one attribute, no visual change — but it's the difference between a screen reader user being able to use your app and being completely locked out.
